## Project overview

E-commerce monorepo:

| App | Package | Port | Role |
|-----|---------|------|------|
| **storefront** | `@apps/storefront` | 3000 | **Active** Next.js storefront (NextMerce UI + Medusa v2.13) |
| **medusa-backend** | `@apps/medusa-backend` | 9000 | Medusa API + admin (`/app`) |

Root `pnpm dev` starts PostgreSQL (`db:up`), runs storefront + medusa-backend, and stops PostgreSQL (`db:down`) on exit.

### Product search architecture

- Storefront live typeahead and `/search` results use Medusa Store route `GET /store/search`.
- Backend route uses an in-memory Orama index (`apps/medusa-backend/src/modules/productSearch`) with 15-minute TTL and subscriber-based invalidation on `product.created|updated|deleted`.
- This path runs inside the existing `medusa-backend` process; no separate search service is required.

### Overridable settings (required pattern)

Every install, edge, Hermes, or deploy setting must stay overridable without editing scripts:

1. **Document** the key in the relevant `environments/*/.env.example` (or `deploy/.env.prod.example`) with a sensible default.
2. **Expose** a CLI flag on bootstrap/install (and/or a documented env var such as `VULPY_*` / `HERMES_*` / `EDGE_*` / `MATOMO_*`).
3. **Read** via `${VAR:-default}` in Compose and shell — never hardcode the only value in a script body.
4. **Prefer** writing the chosen value into the env file at install time so later `hermes up` / `edge up` reuse it.

Examples: `--hermes-port` / `HERMES_PORT` (default `8787`), `--shop-port`, `--api-port`, `--matomo-port`, `--http-port` / `--https-port` (edge behind a load balancer), `--postgres-port` / `--redis-port`, `--dev-label` / `--admin-label` / `--api-label` / `--analytics-label`.

### Tenant resource limits (host-owned ceilings)

Every application (tenant) on a shared host gets a **percentage ceiling** of
host RAM/CPU that the tenant **cannot raise from inside the checkout**:

- **Manifest (root-owned, outside checkout):** `/etc/vulpy/tenants/<appId>.conf`
  — `TENANT_MEM_SHARE_PERCENT` / `TENANT_CPU_SHARE_PERCENT`, set at install via
  `--tenant-mem-share` / `--tenant-cpu-share` (default 25 each).
- **Enforcement:** `sudo bash scripts/vulpy-tenant-limits.sh refresh` computes
  share × host totals and regenerates (a) systemd `MemoryMax`/`MemoryHigh`/
  `CPUQuota` for host dev daemons and (b) a root-owned compose override
  `/etc/vulpy/compose-limits-<appId>.yml` that is loaded last (wins over
  tenant edits) for compose services incl. Fox. `status` prints computed
  ceilings. Missing manifest → no ceiling + warning (backwards compatible).
- **Within the ceiling:** per-service splits are tenant-tunable env vars
  (`VULPY_MEM_SPLIT_STOREFRONT_PERCENT`, `…_MEDUSA_…`, `…_POSTGRES_…`,
  `…_REDIS_…`, `…_FOX_…`, CPU equivalents; defaults in `.env.example` /
  `deploy/.env.prod.example`). Sums over 100% warn and clamp at the share.
- **Watchdog:** `dev-watchdog-host.sh` restarts the dev storefront when its
  RSS exceeds the computed ceiling (`STORE_MEM_MAX_MB` from the generated
  root-owned env file) — restart via `dev-app-server.sh restart`, **not**
  `dev wake` (wake refuses with "Already running" when the stack is up;
  verified EU 2026-08-17). Triggered by the 6.4GB `next-server` growth on the
  EU dogfood box.
- **Desired-state revival (crash + reboot survival):** `dev-app-server.sh`
  writes `.tmp/dev/desired-state` (`running`/`stopped`) on every lifecycle op.
  The watchdog revives the stack (`pnpm vulpy dev up`) when desired=running but
  state ≠ running or status.json is missing — covering crashes, kill-alls, and
  post-reboot wipes — and stays silent when desired=stopped (operator intent).
  It also `docker start`s THIS checkout's stopped core companions (hermes,
  searxng, edge, postgres, redis — matched by compose working_dir label;
  Matomo dev containers deliberately excluded as optional). `start()` runs a
  port-squat pre-flight: clears workspace-scoped leftovers (cwd = workspace OR
  subdirectory) then REFUSES loudly if a foreign process still holds an app
  port — instead of spawning a turbo pipeline doomed by EADDRINUSE. Motivated
  by the 2026-08-26 hectorfinch EU outage: full stack found stopped mid-flight
  (no reboot), a 9-day-old prod-mode `medusa start` orphan squatting :19100
  killed every subsequent dev boot. Boot unit now runs `dev up` (not wake) so
  cold DB containers come up too.

### Application routing boundary

- `VULPY_APP_ID` is the stable cloud application id.
- The regional router/Dokploy target is the single application edge, never an
  individual environment.
- The app network is `vulpy-app-<VULPY_APP_ID>`; never restore a global
  cross-tenant network.
- Staging/live keep private Compose networks and expose only their Caddy
  gateway to the app network. Do not publish environment HTTP/HTTPS ports when
  `VULPY_APPLICATION_INGRESS=1`.
- `pnpm vulpy env sync <name>` regenerates the application-edge route.
- Edge internal mode (`EDGE_INTERNAL=1` in `environments/edge/.env`): the
  application edge mounts `deploy/Caddyfile.internal` (plain `http://` blocks,
  no Caddy ACME) and generated staging/live routes are emitted with each host
  `http://`-prefixed (e.g. `http://shop.example.com, http://www.shop.example.com`),
  because the shared regional router terminates TLS and forwards HTTP to the
  edge preserving the Host header. Default off (`EDGE_INTERNAL=0`) — the edge
  keeps terminating TLS with `deploy/Caddyfile.dev`.
- The app contract (`vulpy-application.json` + `pnpm vulpy app
  ingress-target|validate`) is the product-neutral handoff to the
  router/server layer — see `docs/app-contract.md`.

When adding a new setting, do all of the above in the same change. Do not introduce knobs that can only be changed by patching shell or Compose files.

- **Cart:** `CartContext` + server actions. Do **not** use Redux for cart. Pass `mutation`/`source` to `applyCartResult` after successful cart mutations so Matomo receives authoritative snapshots (not hydration/checkout address noise).

### Idempotent seeds (required)

All seed scripts must be safe to run multiple times on an existing database without errors or duplicate records.

| App | Script | Pattern |
|-----|--------|---------|
| **medusa-backend** | `src/scripts/seed.ts` | Reuse helpers in `src/scripts/seed-helpers.ts` (`getOrCreate*`, `ensure*`, `runIdempotentWorkflow`) |
| **storefront** | `src/scripts/seed-payload-core.ts` | `upsertCollection` / `upsertGlobal` / `ensureMedia` by slug or filename |

When adding new seed data:

1. **Lookup before create** — query by stable key (name, handle, slug, country code) and skip or reuse if found.
2. **Wrap links** — use `ensureLink` or `runIdempotentWorkflow` for workflows that fail on duplicate associations.
3. **Marker-based batches** — for multi-option creates (e.g. shipping options), check one representative name and skip the whole batch.
4. **Verify** — run the seed command twice; the second run should log skips/reuse and exit 0.

Do not call create workflows unconditionally in seed scripts.

## Critical gotchas

### 1. Prices are major units, not cents

Medusa v2 store API returns `calculated_amount: 10` as **€10.00**, not €0.10.

- Use `fromMedusaAmount()` from `money.ts` — **never divide by 100**
- Display via `formatPrice()` (defaults to USD / en-US)

### 2. Publishable key must be linked to sales channel

If storefront gets `400` — *"publishable API key needs sales channel configured"*:

```bash
pnpm --filter @apps/medusa-backend exec medusa exec ./src/scripts/link-publishable-key.ts
```

Ensure `MEDUSA_PUBLISHABLE_KEY` in `apps/storefront/.env` is set — run `pnpm --filter @apps/medusa-backend print-publishable-key` after seed.

### 3. Tax regions exist but add-to-cart / checkout returns 500

Tax regions can exist while `provider_id` is empty. Medusa then fails with *"Unable to retrieve the tax provider with id: null"* when refreshing cart tax lines.

Check:

```bash
docker compose exec -T postgres psql -U medusa -d medusa -c \
  "SELECT country_code, provider_id FROM tax_region;"
```

`provider_id` should be `tp_system`. Fix existing DB:

```bash
pnpm --filter @apps/medusa-backend exec medusa exec ./src/scripts/fix-tax-providers.ts
```

Fresh seeds set `provider_id: "tp_system"` in `seed.ts`.

### 4. Region / empty product lists

If products return empty or prices are missing, check:

1. `MEDUSA_PUBLISHABLE_KEY` is set
2. `defaultCountryCode` matches a seeded country (`us`)
3. `region_id` is passed to product list calls

### 5. Variant ID vs product ID

Cart line items need **variant** IDs (`variant_…`), not product IDs (`prod_…`). Listing mappers set `id` and `variantId` to the variant id for convenience.

### 6. Client/server boundaries

- Medusa SDK calls with `cookies()` belong in Server Components, `lib/medusa/*`, or `"use server"` actions
- Pass serializable props to client components (mapped types, not raw SDK responses with circular refs)

### 7. B2B price gating (optional)

Trade-catalog shops can hide prices and add-to-cart until the customer signs in. **Off by default** (standard B2C shows prices to everyone).

Set in **two places for dev** (same variable name), one for the backend, one for
the storefront bundle:

| Environment | File |
|-------------|------|
| Local dev — Medusa backend | repo root `.env` |
| Local dev — storefront bundle (client flag) | `apps/storefront/.env` |
| Production | `deploy/.env` (injected into both containers) |

```bash
REQUIRE_LOGIN_FOR_PRICES=true
```

**Commercial persona mode.** `PRICE_GATE_MODE` selects the persona with three
values (default `off`):

| Mode | Guest experience |
|------|------------------|
| `off` | Prices public, no gating (default) |
| `login` | Prices hidden; guests see "Login to see price" (legacy flag behavior) |
| `quote` | Prices hidden; guests get a **quotation persona** — "Add to quotation", "Quotation" bag, "Request a Quote" / "Submit quote request" |

`PRICE_GATE_MODE=off|login|quote` (default `off`). Unset `PRICE_GATE_MODE` +
`REQUIRE_LOGIN_FOR_PRICES=true` is treated as `login` (backward compatible).
When `PRICE_GATE_MODE` is set it wins. Same env locations as the flag above.

In `quote` mode, submitting the quotation bag calls store route
`POST /store/quote/orders` (`create-quotation-draft-order` workflow), which
converts the guest cart into a **draft order** tagged
`metadata.quotation = true` — visible in Medusa admin under Orders → Draft Orders.

Also set `NEXT_PUBLIC_ENABLE_CUSTOMER_ACCOUNTS=true` in `apps/storefront/.env` so sign-in is available.

The backend reads root `.env` in dev. The storefront exposes the flag to the client via
`next.config.mjs` `env`, which loads both root and app `.env` — but the **app `.env` is
the reliable source under the turbo dev stack** (verified 2026-08-11 on a tenant box:
root `.env` alone did not reach the Next compile; moving the flag to `apps/storefront/.env`
did). Production injects `deploy/.env` into both containers.

Implementation: `apps/medusa-backend/src/api/store/price-guard.ts` (middleware, env-gated) and storefront `useCanSeePrices()` in `context/AuthContext.tsx`.

**Production:** rebuild the storefront image after changing this flag (`REQUIRE_LOGIN_FOR_PRICES` is baked at build time).

**Not in Medusa admin** — configure via `.env` / `deploy/.env` only.

### 9. Multiple shop clones on one host (Docker port conflicts)

`docker-compose.yml` binds Postgres and Redis to host ports **5432** and **6379**. A second checkout of this template on the same host cannot start its own Postgres until the other stack stops or ports are remapped.

Check what holds the port:

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

Stop the other project (`docker compose -p <other-project> down`) or change host ports + update `DATABASE_URL` / `REDIS_URL` / `PAYLOAD_DATABASE_URL` in app `.env` files.

### 10. Hermes security-gated files require checksum regeneration

Six files are SHA-256 gated by `verify_security_checksums()` in `hermes-fox-entrypoint.sh`. If any of them is edited without regenerating the manifest, `hermes up` **aborts before starting** with `[vulpy] ERROR: Security checksums are stale`. Auto-regen was intentionally removed — it would silently accept agent-tampered files, defeating the gate.

**Any time you edit one of these files, run this before telling the operator to restart:**

```bash
python3 scripts/generate-checksums.py > scripts/.vulpy-security-checksums
```

Gated files:
- `scripts/hermes-fox-entrypoint.sh`
- `scripts/vulpy-agent-cmd-server.py`
- `docker-compose.hermes.yml`
- `docker-compose.edge.yml`
- `deploy/Caddyfile.dev`
- `deploy/Caddyfile.internal`

This is **not** a backend module path — it is the Medusa **Admin UI** i18n extension slot. The admin Vite plugin loads it as `virtual:medusa/i18n` and requires a **default export** (i18next resources merged into stock dashboard copy). Named-only exports crash admin boot (*does not provide an export named 'default'*).

For **backend** custom modules (`src/modules/`, `medusa-config.ts`, migrations, workflows), see **Add a custom Medusa module** below and load the `building-with-medusa` skill — that is a separate extension system from Admin UI i18n.

## Matomo analytics (self-hosted, consent-gated)

Production stack runs Matomo at `MATOMO_DOMAIN` (MariaDB + archive sidecar). Storefront uses a **typed provider bus** (`apps/storefront/src/lib/analytics/`) with Matomo and optional **GTM/GA4 dataLayer** adapters (`NEXT_PUBLIC_GTM_ID`). GTM uses **Google Consent Mode v2** (deny-default; grant on analytics opt-in). Not `@socialgouv/matomo-next` or hardcoded container IDs.

Purchase: Matomo gets a pseudonymized order id; GTM/GA4 gets merchant `display_id` (or order id). Logged-in `user_id` is a hashed customer id only. Coupons are included when promotions are present on cart/order.

### Two data lanes

| Lane | Consent? | Source | Examples |
|------|----------|--------|----------|
| **Matomo (behavioral)** | Analytics opt-in required | Browser after consent | pageviews, search, product/cart/checkout funnel, pseudonymized purchase |
| **Operational reporting** | No browser consent | Medusa `commerceReporting` aggregates | orders placed/paid/cancelled/refunded/fulfilled, units, revenue buckets |

Do **not** send non-consenting visitors into Matomo or reconstruct journeys from server logs. Self-hosting is **not** a consent exemption. Treat GPC as denial.

| Concern | Location |
|---------|----------|
| Adapter / sanitize / ecommerce / events | `apps/storefront/src/lib/analytics/` |
| Consent UI + cookie | `components/Consent/*`, `context/ConsentContext.tsx` |
| Trackers | `components/Analytics/*` (mounted from `SiteLayoutClient`) |
| Privacy / cookie copy | `lib/cms/defaults.ts` (`privacy-policy`, `cookie-policy`); pages `/privacy-policy`, `/cookie-policy` |

### Privacy rules (non-negotiable)

- No Matomo script/request/`_pk_*` cookie before analytics opt-in; withdrawal clears cookies and stops requests.
- Never send email, name, address, raw customer/order IDs, JWTs, card data, or unrestricted query strings.
- Prices are **major units** (same as Medusa — do not divide by 100).
- Purchases: only on order-confirmation via `PurchaseTracker` + `submitPurchaseOnce` (deduped). Do not treat payment-return polling as purchase.
- Cart: emit native cart snapshots only after successful mutations with `applyCartResult(..., { mutation, source })` where `mutation` is `add|update|remove|clear`.

### Add analytics when building new features

**Required for agents:** when adding storefront UX that matters for funnel/engagement (forms, CTAs, filters, drawers, auth outcomes, promotions, new checkout steps), instrument Matomo in the same PR. Load `storefront-best-practices` → `reference/analytics.md`.

1. Prefer existing helpers in `lib/analytics/`:
   - `trackCustomEvent(category, action, name?, value?)` — custom events
   - `trackProductImpression` / `trackSelectItem` — catalog
   - `submitCartSnapshot` via `applyCartResult` mutations — cart
   - Specialized trackers for PDP / search / purchase routes
2. Gate with consent: only fire when `useHasAnalyticsConsent()` is true (or rely on `pushMatomoCommand`, which no-ops without consent + config).
3. Allowlisted payloads only: product/variant/list ids, quantities, major-unit amounts, currency, coarse outcome codes, result counts. Strip free text / PII (`stripPiiFromString`, `sanitizeSearchParams`).
4. Forms pattern (contact, newsletter, account, custom CMS forms):

```tsx
"use client";
import { useHasAnalyticsConsent } from "@/context/ConsentContext";
import { trackCustomEvent } from "@/lib/analytics";

// after successful submit — never include field values
if (hasAnalytics) {
  trackCustomEvent("Engagement", "contact_form_submit", "contact");
  // or: trackCustomEvent("Engagement", "form_step", "shipping_details");
  // validation: trackCustomEvent("Engagement", "form_validation_error", "email_invalid");
}
```

5. Name events consistently: `Category` + `action_snake` (see inventory below). Reuse categories: `Catalog`, `Cart`, `Checkout`, `Wishlist`, `Engagement`.
6. Higher-risk purposes need separate consent (not wired by default): `experimentation`, `marketing`, behavioral diagnostics (heatmaps/replay — disabled).
7. Order lifecycle that must not depend on consent → Medusa `commerceReporting` subscriber lane, not Matomo visitor profiles.
8. Add/extend Vitest coverage under `lib/analytics/*.test.ts` for new mappers/sanitizers.

### Event inventory (summary)

- **Native:** `page_view`, `site_search`, ecommerce view / cart update / order
- **Catalog:** `item_impression`, `select_item`, `quick_view`, filters/sort/pagination, promotions
- **Cart:** `view_cart`, `add_to_cart`, `remove_from_cart`, `update_cart_quantity`, `clear_cart` (+ native cart snapshot)
- **Checkout:** `begin_checkout`, `checkout_details_complete`, `shipping_method_selected`, `payment_method_selected`, `payment_success|failure`, `checkout_error`
- **Engagement:** wishlist, `newsletter_subscribe`, `external_media_play`, auth success/failure (anonymous outcomes only), form step / validation type / submit success
- **Ops-only (Medusa):** `order_placed|paid|cancelled|refunded|fulfilled`, payment/shipping aggregates

## Payload CMS (storefront content)

Payload 3 is embedded in `@apps/storefront` (not a separate app). Admin: http://localhost:3000/admin

| Concern | Location |
|---------|----------|
| Config | `apps/storefront/payload.config.ts` |
| Collections | `apps/storefront/src/collections/` |
| Globals | `apps/storefront/src/globals/` |
| CMS fetch helpers | `apps/storefront/src/lib/cms/` |
| Seed script | `pnpm --filter @apps/storefront seed` |

**Database:** same PostgreSQL Docker container as Medusa, separate database `payload` (`pnpm db:init-payload`).

**Boundary:** Medusa = commerce (products, cart, checkout). Payload = editorial content blocks for pages and PDP extensions.

**Current model:** `pages` (block-based), `productContent` (block-based, synced from Medusa product identity), `categoryContent` (block-based, synced from Medusa categories + pseudo categories like `sale` + admin-created `selection` pages), `contact-submissions` (read-only inbox from contact form), `posts` (richText), plus globals (`site-settings`, `navigation`, `footer`).

**Contact form:** math captcha at `GET /api/contact/captcha` (HMAC via `PAYLOAD_SECRET`); submissions saved to `contact-submissions` via `submitContactFormAction`.

**Selection pages:** Payload `categoryContent` with `kind: "selection"`, custom `route` + `filterQuery`; middleware rewrites public URL → `/selection/[handle]`. `medusaCategoryId` is `selection:{uuid}` and excluded from Medusa→Payload sync.

**Admin crosslinks:** Medusa product/category widgets link to Payload admin + storefront; Payload `productContent` / `categoryContent` expose read-only Medusa admin URLs for synced records.

**Production infra** (`docker-compose.prod.yml`): `storefront_image_cache` volume persists Next.js image optimizer cache. See `deploy/.env.prod.example`.

**Env vars** (`apps/storefront/.env`): `PAYLOAD_SECRET`, `PAYLOAD_DATABASE_URL`, `NEXT_PUBLIC_SERVER_URL`, `PREVIEW_SECRET`, `PAYLOAD_SEED_EMAIL`, `PAYLOAD_SEED_PASSWORD`.
**Env vars** (`apps/medusa-backend/.env`): `PAYLOAD_URL`, `PAYLOAD_SYNC_API_KEY`, `PAYLOAD_SYNC_RETRY_ATTEMPTS`, `PAYLOAD_SYNC_RETRY_DELAY_MS`, `PAYLOAD_SYNC_ALERT_THRESHOLD`. Admin widgets also use `VITE_PAYLOAD_URL` and `VITE_STOREFRONT_URL` at Medusa image build time.

**Dev workflow:** Storefront falls back to `lib/cms/defaults.ts` when Payload DB is empty **in non-production only** (`cmsDefaultsAllowed()`; override with `CMS_ALLOW_DEFAULTS=1|0`). Production must not serve seed chrome on Payload failures — see `lib/cms/fallback.ts` (empty shell by default; `CMS_STRICT=1` to rethrow). With `pnpm dev` running:
- `pnpm --filter @apps/storefront seed` — populate CMS via `POST /api/dev/seed` (idempotent; see **Idempotent seeds** above)
- `pnpm --filter @apps/storefront generate` — write `payload-types.ts` + `importMap.js` via `POST /api/dev/generate` (run after adding collections such as `contact-submissions` or new `categoryContent` fields)

**Schema / migrations:** Dev uses `push: true` (auto-sync). Production uses migration-only (`push: false`). Add schema changes as `.js` files under `apps/storefront/src/migrations/` (`.ts` migrations fail in the production container). Run locally: `pnpm --filter @apps/storefront payload:migrate` (wrapper `scripts/run-payload-migrate.mjs` clears `payload_migrations.batch = -1` so migrate never prompts). Production runs the same via `storefront-entrypoint.sh` using `payload.migrate.config.ts` (minimal config without Lexical). Keep `SKIP_PAYLOAD_MIGRATE=0` unless the DB was restored from a bundle with schema already applied (`=1` is restore-only). After deploy, `scripts/deploy/smoke-storefront.sh` gates the homepage against seed CMS markers.

Payload `generate:types` / `migrate:create` CLI may fail on some Node versions; use dev-server `generate` route and hand-written `.js` migrations when needed.

This project uses **Hermes agent role profiles** to keep AI-assisted coding
structured and reviewable. Profiles live in `~/.hermes/profiles/` and are
created with:

```bash
pnpm vulpy agents setup   # idempotent — safe to re-run
pnpm vulpy agents list    # show all profiles
```

### The four roles

| Profile | Purpose | When to use |
|---|---|---|
| `architect` | Read-only planning — scope, failure modes, implementation steps | Before writing any non-trivial feature |
| `code-reviewer` | Adversarial diff review against this codebase's invariants | Before pushing a PR |
| `qa` | Test plan + gate runner; writes missing unit tests | After implementation, before PR |
| `security` | Auth / Stripe / Matomo / SSRF audit | Any PR touching those areas |

### Invocation

```bash
hermes-architect   "We need product comparison — plan it"
hermes-code-reviewer   # then: "Review my diff" or paste the PR URL
hermes-qa          "Run the test gate and report coverage"
hermes-security    "Audit the new Stripe webhook handler"
```

Each command is a wrapper created by `setup-agent-profiles.sh` that runs
`hermes -p <role> -s <skills>` — profile + skill pre-loads in one shot.
Run `pnpm vulpy agents setup` after install or a container rebuild; it is
safe to repeat, preserves local profile config/SOUL edits, and only restores
missing or invalid requested skill links. Requested links must resolve to the
same-named directory under `$HERMES_HOME/skills` at flat or one-category-nested
depth; unrelated external links and deeper nesting are rejected. Use
`pnpm vulpy agents setup --force` only for an explicit generated-artifact
refresh. Inspect with `pnpm vulpy agents doctor` (read-only), or list profiles
with `pnpm vulpy agents list`.
Or manually: `hermes -p architect -s plan,vulpy-commerce-operator,...`

The default profile (`hermes` with no flags) is the general-purpose implementer
— use it for day-to-day feature work after the architect phase.

## What not to do

- Do not reintroduce mock `shopData.ts` — catalog is Medusa-backed
- Do not put cart state in Redux
- Do not divide Medusa prices by 100
- Do not set `defaultCountryCode` to a country that is not in the seeded region
- Do not force-push `main` or amend commits unless the user explicitly requests it
- Do not create or start live/staging environments from inside Hermes — tell the human to run `pnpm vulpy env add|up|golive` on the server
- Do not load Matomo or emit analytics before consent; do not use cookieless tracking to bypass consent
- Do not send PII / raw order or customer IDs / JWTs to Matomo
- Do not treat payment-return polling as a purchase event
- Do not ship new funnel/engagement UI without analytics instrumentation (or an explicit ops-only Medusa aggregate instead)

## Troubleshooting checklist

1. Is PostgreSQL up? (`pnpm db:up`)
2. Is medusa-backend running on 9000?
3. Is `MEDUSA_PUBLISHABLE_KEY` in storefront `.env`? (`pnpm --filter @apps/medusa-backend print-publishable-key`)
4. Was DB migrated + seeded?
5. Is publishable key linked to sales channel?
6. Does `defaultCountryCode` match seed regions?
7. For checkout: is `NEXT_PUBLIC_STRIPE_KEY` set?
8. For CMS content: is `payload` database created? (`pnpm db:init-payload`) Was Payload seeded? (`pnpm --filter @apps/storefront seed`)
9. For PDP blocks: did you run backend sync (`sync-products-to-payload`) and set `PAYLOAD_SYNC_API_KEY`?
10. For preview: is `PREVIEW_SECRET` set and preview opened via `/api/preview`?
11. Admin blank / i18n console error? Check gotcha §10 — `src/admin/i18n/index.ts` must default-export translation resources; widget copy belongs in `src/admin/lib/labels/`.
12. Bootstrap failed on Postgres/Redis bind? Another shop clone may be using ports 5432/6379 — see gotcha §9.
13. Matomo silent in prod? Check `NEXT_PUBLIC_MATOMO_URL` + `NEXT_PUBLIC_MATOMO_SITE_ID` baked into storefront image (`setup-matomo.sh`), consent accepted, and `https://MATOMO_DOMAIN` healthy.
14. Matomo verify failing? Legal ack (`ack-legal-review.sh`), remove privacy/cookie placeholder copy, re-run `verify-matomo-privacy.sh`.
15. Store customer auth 404/400 on `/store/auth/...`? That's the Medusa **v1** path. Medusa 2.x mounts customer auth at `/auth/customer/emailpass` (login) and `/auth/customer/emailpass/register` — probe those (expect 401 with bad creds, not 404). The storefront SDK already uses the v2 paths; a 404 on the old path is expected, not a broken backend.

## Sync logging retention

Medusa→Payload sync logs are structured (`[payload-sync]`) and intentionally compact. Keep log storage bounded:

- **Container runtime:** set Docker log rotation (`max-size`, `max-file`) for backend service.
- **Systemd/journald:** configure `SystemMaxUse` and/or `MaxRetentionSec`.
- **Cloud logging:** set explicit retention (recommended 14-30 days for sync logs).

Do not log full payload request/response bodies; log identifiers (`product_id`, `handle`, `event`, `status`, `duration_ms`) and concise error codes.

## Cursor Cloud specific instructions

Environment already bootstrapped by the startup update script (`pnpm install`, which also builds `@vulpy/medusa-plugin-email` via its `prepare` hook). Node 22 LTS and pnpm 10.15.0 are the reference toolchain. Standard commands (`pnpm bootstrap`, `pnpm dev`, `pnpm check`, `pnpm test`, `pnpm build`) are documented under **Quick start** and **Scripts reference** above.

Non-obvious caveats for this VM:

- **Docker daemon is not auto-started.** Postgres + Redis run in Docker (see **Quick start**), so before any DB-backed command (`pnpm bootstrap` / `pnpm dev` / `pnpm db:up`) start the daemon once per session, e.g. `sudo dockerd` in a tmux session, then `sudo chmod 666 /var/run/docker.sock`. Docker uses `fuse-overlayfs` with the `containerd-snapshotter` feature disabled (`/etc/docker/daemon.json`) — required for docker-in-VM here.
- **First-time DB bootstrap:** run `pnpm bootstrap` once after the daemon is up (creates `.env` files, starts Postgres/Redis, migrates, seeds Medusa, creates `admin@example.com` / `supersecret`, writes the publishable key to `apps/storefront/.env`). It is idempotent and safe to re-run.
- **Run `pnpm dev` inside tmux.** `scripts/dev.sh` traps EXIT/INT/TERM and runs `docker compose down`, so if the foreground process is killed it stops Postgres/Redis. Keep it in a persistent tmux session; storefront = http://localhost:3000, Medusa API + admin = http://localhost:9000/app.
- **`pnpm check` / `pnpm test` should pass on a clean tree.** If either fails after install, treat it as a real regression (not setup noise).
