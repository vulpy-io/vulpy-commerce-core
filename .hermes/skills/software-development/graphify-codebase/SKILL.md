# Graphify — Vulpy Commerce Knowledge Graph

**graphify** maintains a persistent, queryable knowledge graph of the full monorepo.
Always check the graph before reading raw files for architecture/relationship questions.

## Graph location

```
/app/workspace/graphify-out/          # ENTIRE DIR IS GITIGNORED (line ~68 of .gitignore)
├── graph.html        # interactive (browser) — skipped above 5000 nodes
├── graph.json        # persistent graph
├── GRAPH_REPORT.md   # god nodes, surprises, suggested questions
├── manifest.json     # extraction manifest
├── cache/            # SHA256 cache — gitignored
└── YYYY-MM-DD/       # curated-graph backups (graph.json, report, manifest)
```

**Nothing in graphify-out/ is committed.** The dir is fully gitignored and
regenerated by the post-commit hook. Do not `git add` it. Older skill versions
claimed graph.html/graph.json/wiki were committed — that is wrong for this repo
(verified 2026-08-14).

`wiki/` and `obsidian/` do NOT exist in graphify 0.9.42 — the `--wiki` flag is
a no-op/unknown in this version (it just runs a normal extract; no wiki dir is
written). Ignore any wiki-generation workflow until a graphify version that
supports it is installed.

**graph.html has a 5000-node viz limit.** The Vulpy graph now exceeds it
(~5600 nodes), so `cluster-only`/rebuilds skip graph.html with a
"Skipped graph.html: too large" message. That's expected, not an error.

## Quick commands

```bash
cd /app/workspace

# Query the graph (no LLM needed — reads graph.json)
pnpm graphify:query "how does cart state flow from CartContext to Medusa?"
pnpm graphify:query "what connects the analytics layer to the consent system?"

# Or call graphify directly
graphify query "what are the god nodes?"
graphify path "CartContext" "Medusa SDK"
graphify explain "applyCartResult"

# Node-level inspection
graphify explain "shop-catalog-service.ts"     # 69 connections: imports, callers, related files
graphify god-nodes --top 15                    # most-connected symbols (architectural hubs)
graphify path "CartContext" "checkout"         # shortest directed path (or --undirected)
graphify affected "CartContext" --depth 2      # reverse traversal: what depends on this?
graphify diagnose multigraph                   # structural health: duplicate edges, collapsed pairs

# Update graph after changes
pnpm graphify:update    # incremental (fast, changed files only)
pnpm graphify:build     # full rebuild from scratch

# Re-cluster (no re-extraction) — useful after a big refactor to regenerate GRAPH_REPORT.md
graphify cluster-only /app/workspace

# Build agent-crawlable wiki — NOT AVAILABLE in graphify 0.9.42 (no-op).
# pnpm graphify:wiki still exists but writes nothing useful. Skip it.
```

## Current graph scale

As of Aug 2026: **~24k nodes, ~41k edges, ~1,540 communities** across ~1,900 source files. The graph is well past the 5,000-node viz limit for `graph.html` (skipped automatically). Queries (`query`, `explain`, `path`) work fine at this scale — BFS traversal is fast. `diagnose multigraph` confirms the graph is structurally clean (zero duplicate/collapsed edges).

## Limitations: what the graph does NOT capture (without LLM extraction)

Graphify is **AST-based** — it extracts explicit import/export/contains/calls relationships from source code. Without the LLM semantic pass (`--code-only` mode), it does NOT understand:

| What it misses | Example | Why it matters |
|---------------|---------|----------------|
| **React component composition** | A page rendering `<CartProvider>` from `CartContext.tsx` without a direct JS import | `graphify affected "CartContext"` returns empty — no directed path to checkout pages |
| **Hook chains** | `useCart()` used in a component that's rendered by a layout | No edge between the hook source and the pages that consume it |
| **Server components** | Next.js server components that call Medusa SDK functions | Import relationships exist, but data-flow semantics (server → client) are invisible |
| **JSX template relationships** | `<ProductItem>` accepting `regionId` as a prop | No prop-drilling edges in the graph |
| **Document-to-code connections** | A README describing a feature and the files implementing it | No semantic link between docs and code |

**With the LLM semantic pass enabled** (via Vulpy gateway — see "API keys" section above), graphify infers relationships that AST alone can't see. Run `pnpm graphify:build` with `OPENAI_API_KEY` + `OPENAI_BASE_URL` set to get framework-level edges, document-to-code connections, and semantic relationship types.

**Workaround without LLM:** combine graphify queries with `search_files` (grep) or `read_file` on the component files graphify points to. A directed path query between two React components returning "no path" is expected — fall back to import inspection of the components graphify *does* find. Set `--undirected` when you know the relationship exists but the direction might be wrong (e.g. a parent layout importing a child context).

## Auto-update

The graph self-updates via:
1. **Git post-commit / post-checkout hooks** — installed by `graphify hook install`
   into **husky** (`.husky/post-commit`, `.husky/post-checkout`), NOT `.git/hooks/`.
   Check `git config core.hooksPath` (this repo: `.husky/_`). Rebuilds run
   detached and log to `~/.cache/graphify-rebuild.log`.
2. **GitHub Actions** — `.github/workflows/graphify.yml` — incremental on push to main, full rebuild weekly

### Hook failure mode: silent staleness

The hook rebuilds only *changed* files incrementally. If the base graph has
gaps (e.g. files that failed extraction before, or a fresh install), the hook
alone will NOT backfill them. After installing/enabling graphify, always run
`pnpm graphify:update` once to backfill. Symptom to watch: graph.json mtime is
old despite commits happening → check `~/.cache/graphify-rebuild.log` for
"[graphify hook] could not locate a Python with graphify" (graphify not
installed where the hook looks) or empty re-queues.

### Staleness check

```bash
# Graph mtime vs latest commit:
ls -la /app/workspace/graphify-out/graph.json
git -C /app/workspace log -1 --format='%ad' --date=iso
# If graph.json is older than the last commit → run pnpm graphify:update
```

## When to use

- Before answering "how does X connect to Y?" — query the graph first
- After a big refactor — run `pnpm graphify:update` to capture new relationships
- When onboarding to an unfamiliar module — `graphify explain "ModuleName"`
- To find surprising cross-cutting connections — read `graphify-out/GRAPH_REPORT.md`

## API keys for LLM extraction

LLM extraction (docs, PDFs, images, inferred relationships) requires one of:
- `ANTHROPIC_API_KEY` (default auto-detect priority)
- `OPENAI_API_KEY` (falls back to openai backend)
- `GEMINI_API_KEY`
- `DEEPSEEK_API_KEY`

### Routing through Vulpy gateway

The project's Vulpy gateway is OpenAI-compatible. To route graphify's LLM extraction through it:

```bash
export OPENAI_API_KEY="$(grep VULPY_API_KEY /data/data/hermes/.env | cut -d= -f2-)"
export OPENAI_BASE_URL="https://gateway.vulpy.io/v1"
export OPENAI_MODEL="vulpy-default"      # for inference/semantic extraction
```

Then run `graphify .` — it detects `OPENAI_API_KEY` + `OPENAI_BASE_URL` and uses the openai backend automatically. Community naming can use a cheaper model:

```bash
export OPENAI_MODEL="vulpy-smart"         # for community labeling (cheaper)
graphify label /app/workspace                # renames all placeholder communities
```

The post-commit hook and CI **do not** have these env vars set — they fall back to `--code-only`. Only manual or cron-based graphify runs get the LLM pass.

**Note:** The auto-detect order is `ANTHROPIC_API_KEY > OPENAI_API_KEY > GEMINI_API_KEY` — if multiple are set, graphify picks the first. With `OPENAI_BASE_URL` set, the openai backend is used regardless of key priority.

### No-key behavior

Code-only AST extraction works **without any key** — the `pnpm graphify:*` scripts and CI workflow auto-detect absence and pass `--code-only` silently. No manual flag needed.

## Pitfalls

- **PyPI package is `graphifyy` (double-y).** `pip install graphify` (single-y) installs a different package. Always: `pip install graphifyy` / `pipx install graphifyy` / `uv tool install graphifyy`.

- **Running `graphify .` without an API key fails** when docs/PDFs/images are present: `error: no LLM API key found (313 doc/paper/image file(s) need semantic extraction)`. Fix: use `pnpm graphify:build` (auto-fallback) or pass `--code-only` explicitly.

- **SQL extraction needs an extra package.** `.sql` files produce zero nodes without `tree_sitter_sql`. Fix: `pip install "graphifyy[sql]"`. All extras: `pip install "graphifyy[all]"`.
  - **Installing the extra does NOT retroactively rescue cached-empty files.** Files cached as empty before the install stay at 0 nodes until a re-run picks them up (empties are no longer cached, so `graphify . --update` or any rebuild retries them). Verified 2026-08-14: 3 migration `.sql` files showed 0 nodes right after `pip install "graphifyy[sql]"`; a later re-extract re-queues them. Don't force a full rebuild just for this — the next update/commit hook handles it.

- `graphify` CLI must be on PATH: `pip install --user graphifyy` puts it in `~/.local/bin`
  - Fix: `export PATH="$HOME/.local/bin:$PATH"` or use `pipx install graphifyy`
  - **Background shells (terminal background=true) do NOT inherit this PATH** — run graphify in the foreground or export PATH inside the command.
  - **A background graphify job that dies on PATH notifies LATE.** The completion notification only arrives when the process exits — long after you've diagnosed the staleness and re-run it in the foreground. If you launch graphify in the background, poll it immediately (`process action=poll`) to confirm it actually started; prefer foreground for graphify commands (they're short enough) unless the build is genuinely long-running.

- **Container Python noise:** every Python/graphify invocation in the Fox container prints `Error in sitecustomize; set PYTHONVERBOSE for traceback: PermissionError: ... /usr/local/lib/python3.11/site-packages/sitecustomize.py`. It is a root-owned (`660`) file inside the image; uid 999 cannot read or chmod it. **Non-fatal noise** — graphify works fine. Don't chase it; the entrypoint/image would need a root fix (`chmod 644`).

- The cache dir (`graphify-out/cache/`) is gitignored — incremental runs may redo work on a fresh clone
  - The CI workflow restores the cache via `actions/cache` keyed on `graph.json` hash

- Don't run `graphify .` (full build) on every CI push — use `--update` to avoid unnecessary API costs; the weekly cron handles full rebuilds.

- **Knowledge-pack export creates an untracked directory.** `graphify export` creates a `*-knowledge-pack-YYYY-MM-DD/` dir at the repo root. It is gitignored via `*-knowledge-pack-*/` in `.gitignore`. Delete after use: `rm -rf *-knowledge-pack-*/`.

- **Container file permissions — issue #1 (CLOSED, fully fixed in main).** Files bootstrapped by the host user (`uid=1001`, mode `644`) were not writable by `foxinthebox` (`uid=999`). Fixed in three commits:

  **All fixes applied — nothing to do on fresh installs:**
  - `umask 002` in `scripts/init-project.sh` — bootstrap files (`package.json`, `.gitignore`, `.env` copies) land as `664`
  - `umask 002` in `scripts/graphify.sh` + `scripts/setup-graphify.sh` — graphify output files land as `664`
  - `git config core.sharedRepository group` in `.git/config` — files written by git ops always `664`
  - `hermes-fox-entrypoint.sh` runs `chmod g+rwX` on full workspace at container start (safety net)

  **For installs that predate the fix — run once to sync:**
  ```bash
  cd /app/workspace
  find . ! -path './.git/objects/*' ! -path '*/node_modules/*' ! -path '*/.next/*' \
    ! -name '.env' -type f -perm 644 -exec chmod g+w {} +
  # For host-owned files where chmod fails (can't change owner), use cp+mv:
  # The workspace dir is rwxrwsr-x (setgid group-writable) so rename() works even on 644 files.
  cp AGENTS.md .AGENTS.md.tmp && mv .AGENTS.md.tmp AGENTS.md && chmod 664 AGENTS.md
  ```

  **Emergency workaround A — write-then-rename** (preferred; no divergence):
  ```bash
  # Workspace dir rwxrwsr-x: rename() needs only directory write permission, not file write.
  cp package.json .package.json.new   # or generate new content directly into the temp file
  # modify .package.json.new ...
  mv .package.json.new package.json   # atomic; now owned by foxinthebox, writable
  ```

  **Emergency workaround B — git object store** (last resort; creates working-tree/HEAD divergence):
  ```bash
  git hash-object -w /tmp/updated-file
  git update-index --cacheinfo 100644,<sha>,path/to/file
  # WARNING: disk file unchanged; `cat file` shows old, `git show HEAD:file` shows new.
  # Host user must `git checkout <file>` to sync disk. Always warn the user.
  ```

## Blocker policy

Every blocker or unexpected failure encountered while running graphify tasks must be filed as a GitHub issue immediately — never carry workarounds silently. Use `gh issue create` with: root cause, affected files, impact, fix options with code, and acceptance criteria. Reference the issue number in any commit that uses a workaround.
