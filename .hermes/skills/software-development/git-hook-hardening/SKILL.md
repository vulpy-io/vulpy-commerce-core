# Git Hook Hardening

Diagnosing and fixing repo git hooks that fail outside the original dev
environment (Hermes container, IDE, GUI clients, CI) — and keeping them runnable
so the team actually follows them instead of bypassing with `--no-verify`.

## When to use

- A commit fails inside a hook: `exit 127`, `command not found in PATH=...`,
  `husky - pre-commit script failed (code 127)`.
- Hooks were being bypassed with `--no-verify` and the operator now wants them
  enforced ("fix the hooks, we need to follow them").
- A generated hook (graphify, husky init) crashes only in some environments.
- You need to test a hook without creating a commit, or stage deletions under a
  sparse-checkout path.

## Anatomy of a husky v9/v10 install (this repo)

- `git config core.hooksPath` → `.husky/_` — git runs shims in `.husky/_/`, NOT
  the readable hooks directly.
- Each shim (`_/pre-commit`, `_/post-commit`, …) is `#!/usr/bin/env sh` +
  `. "$(dirname "$0")/h"`. The shared `_/h` prepends `node_modules/.bin` to PATH
  and runs the real hook: `sh -e ".husky/<name>"`.
- The real hooks (`.husky/pre-commit`, `pre-push`, `post-commit`,
  `post-checkout`) are the tracked, editable files. The `_/` shims are generated
  and untracked.
- `set -e` is on in both the shim (`sh -e`) and the hooks themselves — this is
  what turns small command failures into whole-hook crashes.

## Failure 1 — hook tool not on PATH (e.g. `pnpm: not found`)

Hooks inherit the caller's environment; containers, IDEs, and GUI clients often
run git with a stripped PATH (no corepack shims, no pnpm home, no nvm). Symptom:
`./.husky/pre-commit: 4: pnpm: not found` with a PATH lacking the tool's dir.

Fix: make the hook resolve the tool itself — a guarded, portable PATH fallback:

```sh
#!/bin/sh
set -e

# Ensure pnpm is on PATH even in minimal hook environments (containers, IDEs,
# GUI clients) where corepack shims or the pnpm home aren't exported.
if ! command -v pnpm >/dev/null 2>&1; then
    for _d in /usr/lib/node_modules/corepack/shims "$HOME/.local/share/pnpm" "$HOME/Library/pnpm"; do
        if [ -d "$_d" ]; then
            PATH="$_d:$PATH"
            export PATH
            break
        fi
    done
fi

pnpm exec lint-staged
```

This is a no-op on hosts where pnpm is already on PATH. Add the same guard to
every hook that calls `pnpm` (pre-commit, pre-push, …).

### Alternative: PATH shim when hooks are generated/regenerated (verified 2026-08-13)

When the hooks are regenerated by a tool (husky re-init, `graphify hook
install`) OR you shouldn't hand-edit `.husky/*` because it's generated, do NOT
patch the hook file. Instead put pnpm on PATH for the git session — the hooks
inherit the caller's environment:

```bash
mkdir -p /tmp/pnpm-shim
printf '#!/bin/sh\nexec /usr/bin/corepack pnpm "$@"\n' > /tmp/pnpm-shim/pnpm
chmod +x /tmp/pnpm-shim/pnpm
export PATH="/tmp/pnpm-shim:$PATH"
```

Then `git commit` / `git push` work with husky hooks intact. Symptom this fixes:
`husky - pre-commit script failed (code 127)` / `./.husky/pre-commit: 4: pnpm:
not found` inside the Hermes container where pnpm is reachable only via
corepack. The post-commit graphify hook may still fail (no graphify installed)
— that is a graceful-degrade, exit-0 case, harmless.

## Failure 1b — pre-push hook fails inside turbo (`IO error: .turbo/cache`)

Pre-push hooks that run `pnpm typecheck` / `pnpm build` can fail even with pnpm
on PATH when turbo cannot write its cache:

```
✗ IO error: failed to create directory `/app/workspace/.turbo/cache`
  Permission denied (os error 13)
```

`.turbo` is a root-owned bind mount in the Fox container: `rm -rf .turbo` →
"Device or resource busy" (it's a mount point), `chown` fails (no sudo as uid
999). Fix: redirect turbo's cache to a writable dir for the session:

```bash
export TURBO_CACHE_DIR=/tmp/turbo-cache && mkdir -p /tmp/turbo-cache
```

Also: a MID-INSTALL mixed `node_modules` state can make the pre-push typecheck
fail once with unrelated-looking TS errors (e.g. React types mismatch in an
untouched package). After a successful `pnpm install --lockfile-only`, the
rerun passes. Do NOT `--no-verify` for this — fix the cache/environment and
let the hooks run (operator requirement, verified 2026-08-13).

## Failure 1c — husky `_/h` helper missing (shims present, `h` gone)

Symptom (verified 2026-08-17): EVERY hook aborts instantly with
`.husky/_/pre-commit: 2: .: cannot open .husky/_/h` — the commit never even
starts lint-staged. `ls .husky/_/` shows all the generated shims (39-byte
`#!/usr/bin/env sh` + `. "$(dirname "$0")/h"`), but the shared `_/h` helper
is absent.

Cause: `.husky/_` is generated and untracked; a husky re-init, a
`pnpm install` prepare run, or a container rebuild can recreate the shims
without writing `h` (partial husky v9/v10 install). `git config
core.hooksPath` still points at `.husky/_`, so git runs the shims and they
die on the missing source — the real tracked hooks (`.husky/pre-commit`,
etc.) never execute, so editing them does nothing.

Fix: regenerate with the husky CLI in the repo root:
```bash
pnpm exec husky        # pnpm on PATH first (corepack wrapper if needed)
ls -la .husky/_/h      # must exist after regen
git hook run pre-commit
```
Then retry the commit. Check `_/h` exists BEFORE blaming the hook content —
with `h` missing every hook fails identically, and `--no-verify` would mask
the real problem (a broken install, not a failing hook).

## Failure 1d — corrupted corepack shim: shell script wearing a `.cjs` name

Symptom (verified 2026-08-26): EVERY commit fails inside lint-staged with

```
/app/.cache/node/corepack/v1/pnpm/10.15.0/bin/pnpm.cjs:2
exec node /app/.cache/node/corepack/v1/pnpm/10.15.0/dist/pnpm.cjs "$@"
     ^^^^
SyntaxError: Unexpected identifier 'node'
```

and `pnpm <anything>` fails identically when Node resolves that path. Diagnosis:
`head -3 <shim>` shows a POSIX shell script (`#!/bin/sh exec node ...dist/pnpm.cjs`)
but the file is named `pnpm.cjs`, so anything invoking it THROUGH node (lint-staged
spawns, `node_modules/.bin` indirection) executes shell as JavaScript. The real JS
bundle lives next door: `<cache>/pnpm/<ver>/dist/pnpm.cjs`.

Fixes:
1. Repair the cache shim in place: move the bogus one aside, copy `dist/pnpm.cjs`
   over `bin/pnpm.cjs`, `chmod +x`. Verify `node <shim> --version`.
2. Hook-level fallback that survives corepack cache regeneration: write a tiny
   real launcher into the repo — `node_modules/.bin/pnpm` containing
   `#!/bin/sh\nexec node /app/.cache/node/corepack/v1/pnpm/<ver>/dist/pnpm.cjs "$@"`
   (chmod +x). Husky's `_/h` prepends `node_modules/.bin` to PATH, so hooks resolve
   the healthy launcher even when the corepack shim re-breaks after a container
   rebuild. Note `node_modules/.bin` is install-regenerated, so re-add after fresh
   installs or better: keep using Failure-1's guarded PATH block in `.husky/*`.

Distinguish from plain "not found" (Failure 1): here the tool IS found, it just
executes as the wrong language — look at the first line of whatever file the error
path names before blaming PATH.

## Failure 2 — `set -e` + command substitution → exit 127 (graphify hooks)

Classic shell gotcha. Under `set -e`, an assignment whose command substitution
fails kills the whole hook:

```sh
GRAPHIFY_BIN=$(command -v graphify 2>/dev/null)   # command -v exits 1 when missing
```

Symptom: hook dies with `husky - post-commit script failed (code 127)` even when
PATH is complete, because graphify simply isn't installed in that environment.

Fix: `|| true` on the substitution so a missing tool yields an empty variable
instead of a crash:

```sh
GRAPHIFY_BIN=$(command -v graphify 2>/dev/null || true)
```

General rule: **any `VAR=$(... 2>/dev/null)` inside a `set -e` hook needs
`|| true`** (or the command must be inside an `if` condition). Grep generated
hooks for this pattern when they exit 127.

## Failure 3 — lint-staged hangs on generated/minified bundles (biome)

Symptom: `git commit` appears to hang forever (180s+ timeout, zero output);
`pnpm exec lint-staged` run manually stalls at `[STARTED] biome check --write`
after listing the file groups. `git commit --dry-run` is fast, no lock files, no
git processes — the stall is biome parsing a HUGE single-line generated bundle
(e.g. a 776KB built `message-renderer.js`): a single-file run completes fast, the
full staged set hangs. Output is invisible because `git commit ... | tail`
buffers until EOF — a stalled pipe shows nothing.

Diagnosis path (verified 2026-08-12):
1. `git commit --dry-run` fast → not git. `git config core.hooksPath` → `.husky/_`;
   the shim runs `pnpm exec lint-staged`.
2. Run the hook command manually with a timeout; when it stalls, bisect the
   staged set: run biome on all staged files EXCEPT the suspect bundle → seconds
   → bundle confirmed.

Fixes:
- Exclude the bundle from lint-staged with a NEGATED KEY (`!` globs are
  exclusions; the key renders as its own task with the leftover file count):
  ```json
  "lint-staged": {
    "*.{js,jsx,ts,tsx,json,jsonc,css,scss,md,mdx}": ["biome check --write --unsafe --no-errors-on-unmatched"],
    "!extensions/hermes-webui/message-renderer.js": []
  }
  ```
- Also ignore it in biome config: `"files": { "includes": ["...", "!!<path>"] }`
  (double-bang = exclude).
- New dense/injected code dirs hit the same wall on first commit: scope the
  noisy style rules per-directory via `overrides` (repo precedent:
  `apps/storefront/**`, `extensions/hermes-webui/**`), disabling only what the
  dir genuinely violates (noNestedTernary, noNonNullAssertion,
  useDefaultSwitchClause, noExcessiveCognitiveComplexity, noUndeclaredVariables,
  noEmptyBlockStatements, noAlert, useAwait, useTopLevelRegex, ...) with a
  comment stating the dir is gated by its own test suite. Whack-a-mole: re-run
  the suite after each override — expect ~1 more rule to surface each time.

## lint-staged restore conflict on partially-staged files

When a file is BOTH staged and modified (MM) and biome --write reformats it,
lint-staged's restore step fails: `Unstaged changes could not be restored due to
a merge conflict!` → exit 1, `Unstaged changes have been kept back in a patch
file: .git/lint-staged_unstaged.patch`, plus a `lint-staged automatic backup`
stash. The lint TASKS passed — it's only the restore that failed. Fix: `git
stash apply stash@{0}` (restores the kept-back unstaged deltas), then `git add`
the partially-staged files so nothing is MM, then re-run — hook completes, exit
0. After the apply, check for `UU/AA/DD` conflict markers.

## Failure 4 — nested biome config from a vendored submodule breaks `pnpm check`

Symptom (verified 2026-08-14): `pnpm check` fails locally with

```
× Found a nested root configuration, but there's already a root configuration.
  The other configuration was found in /app/workspace.
```

while CI passes. Cause: a **git submodule** checked out at repo root (e.g.
`impeccable/` — a vendored design-detector) ships its own `biome.json`; Biome
walks into it and sees two root configs. CI only passes because
`actions/checkout` without `submodules: recursive` leaves the submodule as an
EMPTY stub (no nested config on disk). Worse: the abort masks ALL other lint
errors — `pnpm check` dies at config-discovery and never reaches real files,
so lint debt accumulates silently.

Diagnosis:
1. `git submodule status` — find the vendored repo at root.
2. `git show HEAD:.github/workflows/ci.yml | grep -B2 -A2 submodules` — CI
   fetch behavior explains why CI is green.
3. `pnpm check 2>&1 | head -5` — the nested-config error is the FIRST error.

Fixes (prefer 1 — root cause):
1. **Migrate the submodule to an npm devDependency** when a published package
   exists and nothing imports it as a module (CLI-only usage). See
   `references/vendored-submodule-npm-migration.md` for the full recipe.
2. **Biome-ignore** the submodule dir: `"files": { "includes": [..., "!!impeccable"] }`
   (bare dir name — Biome's own linter rejects `!!impeccable/**` with
   `useBiomeIgnoreFolder`).
3. Also ignore untracked scratch dirs (e.g. dead `design-concepts/`) the same way —
   Biome walks everything, not just tracked files.

After the migration, re-run `pnpm check` and expect to surface REAL pre-existing
lint errors that the config-abort was masking (this session: 89 errors across
design scripts + webui extensions). Fix them with
`biome check --write --unsafe` then hand-fix the non-auto-fixable (useTopLevelRegex,
noEmptyBlockStatements, useForOf). Watch for unsafe-fix renames (e.g.
unused-var underscore prefix) — verify the rename is consistent before keeping.

## Failure 5 — biome `useAwait` blocks commit on async-without-await wrappers

Symptom (verified 2026-08-19): `husky - pre-commit script failed` with
`apps/storefront/src/app/actions/poll-payment-return.ts:16:8
lint/suspicious/useAwait` — a server action declared `async` whose body only
RETURNS a promise (no `await` anywhere in its own scope):

```ts
// ❌ biome useAwait — async keyword is redundant, body returns the promise
export async function pollPaymentReturnServerAction(): Promise<PollResult> {
  return pollPaymentReturn({ ... });   // pollPaymentReturn is itself async
}

// ✅ fix: drop the redundant async — the returned promise is the action result
export function pollPaymentReturnServerAction(): Promise<PollResult> {
  return pollPaymentReturn({ ... });
}
```

Server actions don't need `async` when they directly return a promise — Next
serializes the awaited result either way. Rule: an `async` function whose body
contains NO `await` (only `return somePromise(...)`) should lose `async`, not
gain a pointless `await`. The inner callbacks can stay async — the rule only
looks at the function's own scope.

Related trap: running `pnpm fix` (biome `--write --unsafe`) to clear a
pre-existing error can silently reformat UNRELATED staged/unstaged files
(import ordering, etc. — this session it touched 11 files). Review
`git diff --stat` after any `pnpm fix`, stage by path, and keep the commit to
the files the task actually changed.

## Testing hooks without committing

`git hook run <name>` (git ≥ 2.36) runs a hook exactly like git would — no
commit needed. Reproduce the stripped-PATH scenario explicitly:

```sh
git hook run pre-commit                 # normal env
env PATH=/usr/local/bin:/usr/bin:/bin git hook run pre-commit   # minimal env
git hook run post-commit
```

- `lint-staged` with no staged files prints "could not find any staged files"
  and exits 0 — that is PASS, not failure.
- A graceful degrade message ("could not locate a Python with graphify
  installed") + exit 0 is the CORRECT behavior for optional tooling hooks.

Final proof is a real commit (with hooks, no `--no-verify`): pre-commit runs
lint-staged, post-commit runs, commit lands.

## Sparse-checkout + skip-worktree interplay

When a repo uses sparse checkout (`.git/info/sparse-checkout` with `!dir/`
patterns) or `skip-worktree` flags, `git status` SILENTLY ignores changes under
those paths — deletions, modifications, even new untracked files may not show.
That's how committed broken symlinks went unnoticed for weeks.

Detect:

```sh
git ls-files -v .hermes/skills/building-storefronts   # 'S' prefix = skip-worktree
git config core.sparseCheckout
cat .git/info/sparse-checkout                          # e.g. '/*' + '!.hermes/skills/'
find repo-dir -xtype l                                 # broken symlinks: count should be 0
```

Stage changes under sparse-excluded paths:

```sh
git update-index --force-remove -- <deleted-skipped-paths>   # stage deletions of skip-worktree files
git add --sparse -- <new-paths>                               # stage additions in excluded dirs
```

`git add <path>` alone fails with `pathspec did not match any files` for
deleted skip-worktree entries — use `--force-remove`, not plain `git add`.

## Regeneration trap

Hooks installed by a tool (`graphify hook install`, husky re-init) get
OVERWRITTEN from the tool's template, silently reverting your fixes. After
patching a generated hook: (a) note it in the commit message, and (b) file the
fix upstream against the tool's template so reinstalls don't reintroduce the
bug.

## Pitfalls

- `_/h` prepends a RELATIVE `node_modules/.bin` — fine because git runs hooks
  from the repo top-level; don't "fix" it.
- Post-commit/post-checkout hooks that are best-effort (background rebuilds)
  must exit 0 when their tooling is absent, or they block every commit flow.
- `--no-verify` is a last resort, not a habit: if the operator says hooks must
  be followed, fix the hooks (see above) and verify with a real commit.
- Container PATH vs host PATH differ; always test hooks with a stripped PATH
  (`env PATH=... git hook run ...`) to prove they work where the operator's
  IDE/GUI/agent runs git.

## Verification checklist

1. `git hook run pre-commit` and with stripped PATH → exit 0
2. `git hook run post-commit` / `post-checkout` → exit 0 (graceful message OK)
3. Real `git commit` (no `--no-verify`) → pre-commit + post-commit both run
4. `find .husky -xtype l` clean; hook files tracked and committed
